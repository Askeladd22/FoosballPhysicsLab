# PAUL 21-01 — Table Soccer local 2.5D + zero-friction rod switching

**Date:** 2026-11-20. **Branch:** `feature/table-soccer-local-mesh-and-auto-rod`, based on `b6a9074e`.
**Product:** Foosball Lab only. NEON 11 frozen. No career/rankings.

## Evidence from supplied ZIP (SEED)
- `Table_Soccer.zip` contains Maya .ma/.mb, FBX, and OBJ + material textures. The OBJ explicitly declares **29 named geometric groups** including `TS_Main`, `TS_Field`, `TS_Ball`, and independent blue/red goalkeeper, defence, midfield, attack groups. Geometry uses centimeters, Y-up, rods align with model X, play length is model Z.
- Readme by **Hend Z. / VERTX3D (June 2014)**: Maya source has configured rod rotation/slide limits. OBJ exports **lose pivots and limits**. Usage commercial/non-commercial allowed, **redistribution or sale of the model in whole or in part prohibited**.
- **DECIDED:** do not commit source ZIP, OBJ/FBX meshes, exported sprites or derivatives to this public repository. Provide an offline local baker that accepts the user's own ZIP, creates ignored PNGs locally, and falls back to procedural Neon Glass whenever not installed.
- **DECIDED:** physics remains the existing 120 Hz 2D model with physical front-foot geometry; local mesh sprites are visual only, anchored to each current 2D rod/figure; no hidden 3D colliders or teleporting.
- **DECIDED:** default rod control `AUTO` predicts ball position, selects nearest useful **human** rod with hysteresis, cooldown and a short no-switch window during deliberate mouse motions. Mouse wheel/1–4 choose `MANUAL`, Tab restores AUTO; the mouse Y/X still translates/rotates only the selected rod. This avoids needing four hotkeys continuously.
- **UNVERIFIED:** precise visual identity of exported meshes at all rod angles, native Windows performance, subjective feel and fairness. Native playtest required; offline sprite baking is not an engine migration.

## PLAN — acceptance criteria
- **AC1** [selector.lua, model.lua]: AUTO chooses among rods 1–4 based on ball position/predicted velocity and reachable Y lane; 0.2+s cooldown and hysteresis prevent oscillation, deliberate mouse gestures prevent mid-strike switches; never controls opponent rods. Manual wheel/keys remains sticky until Tab. Pure Lua tests.
- **AC2** [offline baker]: reads actual user OBJ from ZIP and named groups; can generate table backdrop, each blue/red rod at a range of angles and ball visual as transparent PNGs. **No source/derived binaries committed**. Includes an inspect-only CLI, no untrusted execution, and manifests source hash/attribution.
- **AC3** [mesh_art.lua, main.lua]: optional 2.5D sprites are loaded only if generated files exist, correctly drawn at rod X/slide, with flat physical foot front edge kept as an overlay. G keeps glow toggle; V toggles 2.5D / procedural view. No visual files needed for first launch. tests mock rendering and fallback.
- **AC4** [docs, CI]: usage, clear rights limitations, local conversion steps, scores/physics and 11vs11 tests all preserved, Lua5.4/LuaJIT and converter inspector self-test pass.
- **AC5** Human UAT: 10 aimed shots while AUTO selects rods, compare automatic vs manual control and V on/off at 1280x850; count unwanted changes in one swing, missed balls, visual foot misalignments and frame-time slowdowns. **NOT_RUN** until user tests.

## Stop rule (Game Design Lab)
If automation selects the wrong rod often or distracts the player during a shot, disable AUTO by default or require a one-button tap-to-switch. If mesh sprites obscure the physical front-foot collision or tank FPS, stay with procedural Neon Glass. A green CI is not proof that the new art/control feels better.
